#+title: theme

This file explains =theme.el=. It holds the HTML *structure* templates for this site, in one file. No
site configuration lives here. =site/site.el= supplies the menu items, colors, tags, and other
configuration as arguments to these functions. See the top-level =README.org= for how to load and build the site.

* For everyday edits
To change how the site looks, edit the CSS files directly. =theme.el=
never sets colors or a =<style>= block.
- The main stylesheet: =assets/css/theme.css=. The look is called *Kenbun* (reading first), which replaced *Hakimacs* (the fake Emacs frame) on 2026-11-19; see =docs/css-design.org=. Elements get their look from =@layer base=; a short list of primitives covers the rest. Components read only the colour aliases in =@layer tokens=, never raw =--baseXX=.
- The wander-console stylesheet: =assets/css/wander-theme.css=.

Edit these files with normal CSS tools. Nothing in them is generated.
This site no longer reads CSS from the =themes/emacs/= submodule. Hugo,
which that submodule belonged to, is fully retired.

To change JS behavior on the site, edit =assets/js/index.js= directly.
This is the one real JS file, plain-copied into the build. =theme.el=
only points a =<script src>= at it.

* For developers
** Sexp-HTML, explained

A template in this file is a plain Lisp list:
=(TAG (:attr "value" ...) CHILD1 CHILD2 ...)=. For example,
=(a (:href "/" :class "site-title") "Home")= becomes
=<a href="/" class="site-title">Home</a>=. A bare string is a text
node, escaped for HTML automatically. =(raw-html nil "<b>already
html</b>")= inserts already-rendered HTML without escaping it. Post
bodies from org-export use this. Small template functions build up
bigger sexp trees. Then =denden-serialize-node= (in =denden.el=) turns
the final tree into an HTML string when the site is published.

** Why not plain HTML files with placeholders?

A plain Lisp list is real data. It composes with =append=, =list=, and
=mapcar=, like any other Lisp value. A malformed list, for example a
dotted pair where a list of children was meant, is a build-time error
from =denden-normalise-attributes=. It does not silently break a page.

The tradeoff: a template reads less like HTML at first glance. If that
is a problem, use =denden-convert-html-file= or
=denden-convert-html-string= (in =denden.el=). These functions turn real
HTML back into this sexp form. This is useful for sketching a piece of
markup as plain HTML first, then converting it in.

** What is in here, top to bottom

- The page shell (=theme-baseof=). =body > header= holds the site title (sways on hover, a random quote in its tooltip) and two rows: the =site-menu-header= links, then the icon toolbar (width, font, scheme, dark/light, random, M-x) with the toast. =main= holds the page. =body > footer= lists every page from =site-menu-main= (=nav#all-pages=) and the footer content. Then the command-palette dialog, and the pre-paint script in =<head>= that applies the stored scheme, variant, font and width before the first paint.
- A single post or page. The post header, references and See Also, the
  comment box, and previous/next navigation.
- Listing pages. The article list, the tags page, and term pages.
- Topic-list pages. The shape used for wander, projects, media, quotes,
  uses, and the sitemap.
- The Pose page. One folded entry per day ("date :: title" heading, rest in =<details>=), the newest open.
- The Wander launch link and its console dialog (=theme--wander-launch=, =theme--wander-dialog=).

** Primitives: new pages reuse these
Every page is built from these and plain elements. A new page or new
structure must reuse them. If it seems to need new CSS, fix the primitive
instead of adding a page-specific rule.
| primitive           | markup                                             | built by                                   |
|---------------------+----------------------------------------------------+--------------------------------------------|
| list                | =ul.list= / =ol.list= of rows; groups are =section= + =h2= | =theme--page-row=, =theme-topic-item=          |
| list controls       | filter =input[data-filter]= + view radios            | =theme-list-filter=                          |
| heading with # link | =h2[id]= + =a.heading-anchor=                          | =theme--heading=, =denden-headline=            |
| pager               | =nav.pager= with =rel= prev/next                       | =theme-post-navigation=                      |
| callout             | =div.callout[role=note][data-callout]=               | =denden-special-block=                       |

** How the CSS pipeline works
Most CSS is hand-edited, in =theme.css=, named above. Two small parts
are generated instead, both in =site.el=:
- =site-scheme-css=. The base16 color variables for each scheme.
- =site-highlight-stylesheet=. The code-highlight color mapping.

Both are short =[data-scheme="x"]{--base00:#...;...}= blocks, one per
scheme. At build time, =site-build-stylesheet= joins =theme.css= and
these two generated blocks into =public-denden/css/bundle.css=. Each
part sits under its own comment banner. Open that file after a build to
see exactly what shipped.

** JS-only controls
Controls that need JS (the toolbar, list filters, view radios) render
with =hidden= and =data-requires-js=; =index.js= reveals them. One
shared filter in =index.js= serves every list: it hides rows by their
=data-filter-text= and hides a =section= once all its rows are hidden.
The view radios (List, Grid) work through CSS =:has()= alone; JS only remembers the
choice.

Every setting change shows a short toast: a native =popover= with =role=status=, so screen readers hear it too (=announce= in =index.js=). Toolbar buttons and content buttons share one =data-action= table; older action names used inside content pages (=browse-schemes=) still work.
